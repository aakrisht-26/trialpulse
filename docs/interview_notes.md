# Interview notes

One entry per roadmap step: what was built, the key decision and why, the rejected alternative and why not, and one likely interview question with a short answer.

## Step 1: Repo skeleton, tooling, CI

**What was built.** A uv project on Python 3.12 with a src layout and a typed `trialpulse` package. Configuration is split in two: `config/project.yaml` holds the locked study definitions (population, event statuses, landmarks, horizons, walk-forward origins, metric constants, seeds), and a `Secrets` model reads credentials from the environment. Also: pre-commit hooks for ruff, mypy and file hygiene; a GitHub Actions CI job (lockfile install, lint, format, strict types, tests with coverage); a Postgres 16 container with a healthcheck; ADRs; and the progress log.

**Key decision and why.** The locked constants live in a committed YAML file validated by a strict, frozen schema, and environment variables cannot override them. A commit then fully determines the definitions a run used, which matters because the whole project depends on outcome and time definitions staying fixed across dozens of runs. Validators catch inconsistent definitions early, for example a horizon that does not land on the discrete-time interval grid, where the CIF would be undefined.

**Rejected alternative and why not.** A single settings class where environment variables override every value. It is convenient for experiments, but a leftover shell variable could silently change a locked definition. The results would then no longer match the committed config, and that is very hard to detect afterwards.

**Likely interview question.** "How do you make sure an experiment ran with the constants you think it did?"

**Short answer.** The constants are in a version-controlled file, loaded into an immutable schema that rejects unknown keys and ignores the environment. A smoke test pins the locked values, so changing one fails CI until the change goes through an ADR. Later steps log the git commit and the pinned dataset revision with every run, so any result traces back to the exact definitions and data.

## Step 2: Feasibility spike

**What was built.** A spike, runnable part by part, that checks whether the plan can work before any pipeline is built: it downloads and profiles the version-history dataset, counts the cohort and early stops, compares a seeded sample against the official API, audits how often list fields change after a trial's first version, and exercises the live API v2 delta pull. Each part writes its numbers to a results file, and a report is generated from those files. Every HTTP call is rate limited, retried with backoff and cached, so a crash or network outage costs only the requests in flight.

**Key decision and why.** Parts that cannot run are recorded as "blocked" with a reason instead of failing the whole run. Overnight, the dataset access request was still awaiting the authors' review, and the spike still produced real API numbers, a working delta pull and the stability audit. The report states each criterion as met, not met, or blocked, so a missing input is never mistaken for a passing one.

**Rejected alternative and why not.** Pulling the 200 part d records one by one from API v2. The cohort-wide bulk pull already holds the same official fields for all 420,073 cohort trials, so part d reads them from that Parquet file and only calls the API for trials missing from it. That saves 200 requests and keeps both sides of the comparison from the same snapshot.

**Likely interview question.** "Your registry data rewrites itself after a trial stops. How did you check that the version history is trustworthy before building on it?"

**Short answer.** Three independent checks: an automated comparison of the dataset's latest version against the official API for a seeded sample, counting a mismatch only when the official record was not updated after the dataset cutoff; a manual comparison of version 0 against the registry's own Record History page; and a stability audit that measures, from real version histories, how often fields that lack history in the dataset change after registration. A field is allowed only if it changes in under 3% of trials.

## Step 6 (partial, provisional): Why trials stop

**What was built.** The eight-label taxonomy with definitions and tie-break rules, a labeling guide, a seeded sampler for the 400-text gold set (stratified by status and stop year, split 100 dev and 300 test), and a Streamlit app that shows one text at a time and saves each label at once, keyed by trial and text hash, without the text. After the PR review the texts come from the current API v2 records of the cohort's early stops, normalized and deduplicated, so labeling does not wait for the version-history dataset; the real 400-text sample is built, and the logic is tested on synthetic data, including the app itself through Streamlit's test harness.

**Key decision and why.** Labels are stored separately from texts, keyed by (nct_id, text_sha256), the SHA-256 of the normalized text, with the pull date as source, so they survive a later change of history source. The labels file can be committed and reviewed, while the texts stay under the gitignored data folder, which respects the dataset license and keeps the repository free of redistributed content.

**Rejected alternative and why not.** Sampling uniformly at random. Early stops cluster in some years (and COVID-19 created a spike), so a uniform sample could leave small strata empty. Proportional allocation with at least one item per non-empty stratum keeps the gold set representative and still covers rare cells.

**Likely interview question.** "How do you know your LLM labels are good enough to train on?"

**Short answer.** A gold set of reference labels from an adjudicated model panel, split before any prompt work: 100 texts for prompt development and 300 held out. The LLM and the distilled classifier are scored once on the held-out 300 with macro-F1 (with a bootstrap interval), Cohen's kappa and a confusion matrix, and the target (macro-F1 of at least 0.80) was declared in advance.

## Step 8 (provisional): Evaluation harness and test lock

**What was built.** Inverse probability of censoring weights from a Kaplan-Meier estimate of the censoring distribution; IPCW time-dependent AUC and Brier score at a horizon; calibration against Aalen-Johansen by risk decile, plus slope and intercept; lift at 10%; a cluster bootstrap that resamples trials; the walk-forward runner; M0 (Aalen-Johansen per stratum); and the test lock from ADR 0004. Metric tests use synthetic data with known answers, including a hand-worked censoring example (IPCW AUC 0.625 against 2/3 unweighted).

**Key decision and why.** The lock is checked before any data is loaded, and it trusts only an annotated git tag on a commit whose registration is complete and is an ancestor of the code being run. A header stub or a later edit cannot satisfy it, and every locked run records the exact commit it was registered at.

**Rejected alternative and why not.** Using 1 minus Kaplan-Meier for the early-stop probability. With competing completions, it treats completed trials as if they could still stop and overstates risk; Aalen-Johansen weights each stop by the probability of still being open just before it.

**Likely interview question.** "Most of your trials have not finished yet. How is your AUC not biased?"

**Short answer.** Rows censored before the horizon get weight zero, and every row whose outcome is known is weighted by the inverse probability of remaining uncensored until its event time or the horizon. That makes the known outcomes stand in for the unknown ones. Without censoring every weight is 1 and the metric reduces to the ordinary AUC, which a test checks.

## Step 6 (continued): Reference labels from an adjudicated model panel (ADR 0010)

**What was built.** The 400-text gold set now holds reference labels from an adjudicated model panel instead of hand labels. Three independent labeler agents label each text, seeing only the labeling guide and the text under an opaque id, and each quotes the deciding words and gives a one-line justification. A fourth agent that labeled nothing decides every split from the text, the guide and the three justifications. A fresh labeler then relabels a seeded 10% as a consistency check. The code prepares the inputs, validates the outputs, resolves labels and panel outcomes, and writes the labels file with a method and a panel-outcome column. A guard test fails if any test text appears in the LLM prompt files. Results: 93.8% unanimous, 5.5% kept by the adjudicator, 0.8% overturned, and 39 of 40 consistency relabels agreeing (kappa 0.969).

**Key decision and why.** The test labels were finished and committed before any prompt work, and the orchestrating session never saw a test text: the agents read the files themselves, and the workflows and collection scripts passed only counts back to it. That keeps the held-out 300 genuinely held out, which is the whole point of a test split. The model graded against these labels must come from a different model family, because a model from the panel's family would share its habits and inflate agreement.

**Rejected alternative and why not.** Majority vote with no adjudicator. Two labelers from the same model can make the same mistake, so the adjudicator judges the justifications against the guide and may overturn a 2-to-1 vote; it did so 3 times.

**Likely interview question.** "Your gold labels came from a model. How do you know your LLM results mean anything?"

**Short answer.** I describe them honestly as reference labels from an adjudicated model panel, not human labels, so the metric measures agreement with a documented, auditable process. The panel ran under strict isolation (audited from the agent transcripts), every label has quoted evidence, splits were adjudicated rather than voted, and a consistency relabel measured stability. The graded model comes from a different family, so it cannot score well just by sharing the panel's biases, and the test split was frozen and committed before any prompt work.

## Step 6 (continued): LLM labels and the distilled classifier

**What was built.** An LLM labeler for why_stopped texts (openai/gpt-oss-120b on Groq, temperature 0, strict JSON-schema output validated in code, batches of 25, every answer cached by request hash so runs resume within the free tier's daily limits), a scoring module (accuracy, macro-F1 with a bootstrap interval, kappa, per-label F1, confusion matrix), and a distilled TF-IDF plus logistic regression classifier trained on the LLM's labels of a 10,000-text sample. Guards run before any call: the rendered prompt must contain no gold-test text, the model must come from a different family than the reference panel, and test items are labeled only with a committed prompt. Each model is scored on test once.

**Key decision and why.** The prompt was tuned on the 100 dev items only, with the selection rule declared first, and frozen in a commit before any test item was labeled. Dev macro-F1 went from 0.858 to 0.980 in two iterations, but test macro-F1 was 0.842: the gap is the optimism of tuning on the same 100 items, which is exactly why the test split stayed untouched. The production model is the distilled classifier, not the LLM, because it is free, fast, deterministic and runs offline.

**Rejected alternative and why not.** Adding few-shot examples copied from the dev items. They would have made the dev score meaningless (the answers would be in the prompt), so v2 states general rules drawn from the dev errors instead, and the third allowed iteration was not used because the two remaining dev errors were single hard cases.

**Likely interview question.** "How do you know your prompt engineering did not overfit?"

**Short answer.** I declared the rule for choosing the prompt before running it, iterated only on a 100-item dev split, froze the prompt in git, and then scored once on 300 held-out items that were never opened during prompt work, with a bootstrap interval. Dev said 0.98 and test said 0.84: the held-out number is the one reported, and the gap itself shows why the split matters.

## Step 2 (completed): an automated version check and the GO decision

**What was built.** Part e of the feasibility spike now checks the version history automatically: 50 seeded trials, version 0 and one random later version of each, fetched from the same internal history source the dataset was built from and compared field by field (submitted date, status, study type, first posted, start and primary completion dates, enrollment count and type, sponsor class) at the dataset's date precision. 899 of 900 fields agree; the one mismatch is the registry's UNKNOWN status, which it sets without posting a version. Every automated criterion passed, so Step 2 is GO.

**Key decision and why.** Replace a 10-trial manual check with a 100-version automated one (ADR 0011). The registry's Record History page shows the same internal source, so a person clicking through pages adds no independence, only a smaller sample and hours of work. Every mismatch must have a named cause, so the check cannot pass on a share alone while hiding a systematic error.

**Rejected alternative and why not.** Checking against API v2 only: it serves the current record, so it can never confirm what version 0 said, which is exactly what point-in-time reconstruction depends on.

**Likely interview question.** "Your whole approach depends on a third-party version-history dataset. How do you know it is right?"

**Short answer.** Three independent checks before building on it: the latest version of 200 random trials against the official API (99.3% agreement), the version lists and submission dates of 150 trials against the official change logs (973 of 973 dates), and 100 random historical versions against the official history source (99.9%). Every disagreement was traced to a named cause, mostly the registry setting UNKNOWN without a new version, which is itself a finding the model design now handles.

## Step 3: Warehouse, contracts and live schemas

**What was built.** A DuckDB warehouse built from the pinned version-history revision: `raw_versions` (only the columns a planned feature, label or audit needs, each typed explicitly), `texts` (every distinct normalized text once, keyed by SHA-256), `versions` (canonical rows validated with Pandera), `versions_quarantine` (rows that fail, with reasons), `trials` and `build_info`. One canonical version contract serves both the offline dataset and live API v2 records, including a content hash that is identical for an unchanged record from either source. Alembic creates the empty live, serving and monitoring schemas in Postgres, and a generated data audit reports duplicates, version order, impossible dates, enum drift, status reversals and personal-data handling.

**Key decision and why.** Make the two sources meet in one canonical form instead of comparing them loosely. The dataset stores most text as HTML and API v2 returns Markdown for the same record, so the contract reduces both to one plain text (one line per paragraph or list item). On live samples of 259 trials the normalized texts agree on every field, which is what lets the daily job tell a real amendment from a formatting difference, and lets the serving-parity test in Step 14 be exact.

**Rejected alternative and why not.** Loading all 96 columns "in case". It would copy personal data (investigator names, emails in free text, people named as sponsors) into the warehouse and every derived artifact. Loading only what a planned use needs, dropping personal columns at the source and scrubbing emails from kept text makes privacy a property of the pipeline rather than a promise.

**Likely interview question.** "How do you know your warehouse build is reproducible?"

**Short answer.** Every table is deterministic by construction (sorted inputs, hash-keyed texts, no timestamps in tables), and the build computes each table's row count and an order-independent checksum, then compares them with the previous build. Building twice from the same pinned revision gives identical checksums, independent of the number of worker processes, which a test also checks on a synthetic dataset.

## Step 4: Cohort, outcomes and landmarks

**What was built.** The cohort, point-in-time, from the canonical version history: each trial's outcome (the first terminal version decides early stop or completion; reversals are excluded), landmark rows every 6 months from registration (kept only if the trial is interventional, open and uncensored on that date, judged from the version in effect then), the evaluation label per landmark in the exact format the evaluation harness reads, and person-period rows (four 6-month intervals per landmark) for the discrete-time models. 330,121 trials, 1,448,969 landmark rows and 4,245,278 person-period rows, built in about 18 seconds from the warehouse. M0 then ran end to end through the harness on the development origins (AUC at 12 months 0.543 and 0.551).

**Key decision and why.** Derive UNKNOWN from the registry's own rule on versioned fields instead of trusting the registry's label (ADR 0014). The dataset turned out to store the registry's computed UNKNOWN over the latest version's submitted status: all 84,976 UNKNOWN versions are latest versions, 37,495 trials show it on version 0, and the rule holds at the version's own post date for only 172 of them. Used as a label, it would have removed tens of thousands of trials from the risk set from registration on, and it goes stale, because the registry sets it without posting a version. The derived rule reproduces all 84,976 labels, agrees with the live registry on every sampled trial, and runs the same way offline and live.

**Rejected alternative and why not.** Censoring a trial at its first lapse, even when a later version resolves it. 43,348 trials lapse and then post another version, and 39,919 of those end with an observed outcome or are still open (often a late completion). Censoring them at the lapse would throw away outcomes that were actually observed and bias the cohort against sponsors who report late.

**Likely interview question.** "How do you know your labels do not leak the future into past prediction dates?"

**Short answer.** Every landmark is judged only from the version in effect on that date: its study type, its submitted status, and whether the registry's 2-year verification rule had lapsed by then. The label (what happened later) is the only thing taken from the future, and it lives in two columns the models never see as features. Hand-built mini histories test each rule, including a study type that changes after registration, a status reversal, and a trial that becomes unknown without the registry ever saying so.

**What the independent review caught.** Two reviewers re-derived the cohort from the ADR text (0 mismatches over 604,583 trials) and still found a real bias: person-period intervals cut short by the end of observation kept their events and dropped their continuations, which inflated the no-covariate CIF by 4% (0.0332 against Aalen-Johansen's 0.0318). The fix is one rule (an interval counts only if it ended within the observation window), a synthetic test that compares the discrete CIF with Aalen-Johansen, and ADR 0015. Mutation testing by the second reviewer showed 15 rule changes that no test noticed; each now has a test.

## Step 5: Exploratory data analysis

**What was built.** One command (`uv run python -m trialpulse.eda.report`, about 15 seconds) that regenerates `docs/eda.md` and nine figures from the Step 4 cohort and the warehouse: early-stop cumulative incidence by sponsor class, registration year, landmark and registration timing; the stop-versus-complete view; what the record showed at the 12-month landmark and what followed; registration lag; estimated post dates; and a descriptive look at the COVID period. Modeling-relevant numbers read nothing dated 2018-01-01 or later, and the phase and COVID sections are labeled descriptive only. The report ends with eight findings, each with its modeling implication.

**Key decision and why.** Make the report checkable instead of trusting its prose. Every sentence that carries a number formats it from the same results that fill the table it cites, and every direction a finding states ("industry trials stop early sooner", "the base rate is stable") is verified against the numbers before anything is written. If a new dataset revision stops supporting a sentence, the command refuses and names the claim. An EDA document usually goes stale silently; this one cannot be regenerated into a false statement, and a test compares the committed report with a fresh regeneration.

**Rejected alternative and why not.** A notebook with hand-written conclusions. It is the usual form for EDA, but its conclusions are typed once and never rechecked, it mixes the locked test years into plots unless someone remembers not to, and it cannot be tested. A generated report takes more code. In return the rule "nothing dated 2018 or later" lives in the functions and is proven by tests on a synthetic registry with known answers, including a point-in-time test that rewrites every version posted after the landmark and shows that no amendment signal changes.

**Likely interview question.** "What did the EDA change about your modeling plan?"

**Short answer.** Three things. Completion is the common ending (74% within eight years), so treating it as censoring would double the apparent early-stop risk (29% against 14%); that is why the targets are competing-risks quantities. At the 12-month landmark a trial's status separates risk far more than date edits: a suspension on record means 24% early stops within two years against 7%, still not recruiting 13% against 6%, while a later completion date moves it only from 6% to 8% and is as common before a completion as before a stop. And trials registered before they start carry about twice the risk of trials registered over a year late (5.9% against 3.0% at 24 months), almost entirely through withdrawals, because a late registrant has usually passed the point where trials are withdrawn; registration timing therefore has to be a feature, or the model would read survivorship as low risk.

**What the independent review caught.** No number was wrong (both reviewers re-derived the tables), but several readings were. One finding explained the higher 2008 rate by registration timing when the data showed the opposite. "Enrollment target cut" mixed real target edits with final enrollment below target, and the pooled comparison (6.8% against 6.8%) hid the strongest contrast in the table: among trials whose enrollment had closed, those 10% or more below their first target stopped early seven times as often. And the "landmarks before 2018" rule still let outcomes from the locked years into modeling-relevant tables (40% of the early stops), so outcomes are now censored at 2018-01-01 as well. Mutation testing showed that 55 of 95 code changes went unnoticed by the first tests; the tests now compare the SQL with an independent Python twin on a registry that has a case on every boundary.

## Follow-up to Steps 4, 5 and 8: training labels as of each origin, censoring weights by sponsor class (ADRs 0016 and 0017)

**What was built.** Two changes to how models are trained and scored, both asked for in the review of Steps 4 and 5. First, the cohort build now writes, for each walk-forward origin T, the cohort as it would have been built on T: only versions posted before T are known and observation ends on T. Those files are the training rows; the harness refuses training rows dated after their origin. Second, every IPCW metric weights a row by a censoring curve fitted within its lead sponsor class, and reports the single-curve values beside it as a sensitivity check. M0 was rerun on the development origins: AUC at 12 months 0.544 and 0.552, against 0.543 and 0.551 before.

**Key decision and why.** Build each origin's training set from what was posted before the origin, with the same code as the final cohort, instead of truncating the final cohort at the origin. Truncation hides later events, but three things were still decided with hindsight: whether a trial that looked lapsed on T later reported again (the UNKNOWN rule), whether a trial was later excluded for a status reversal, and whether a later version said it was interventional. About 8% of the training rows at the 2016 origin exist in only one of the two versions (13,968 only as of T, 19,314 only with hindsight, of about 400,000). A model retrained in production on date T cannot have the hindsight rows, so the backtest should not have them either.

**Rejected alternative and why not.** Keep the truncated labels and state the limit in the model card. On the numbers it was defensible: no event label differs on a row both versions hold, and M0's AUC is the same to four decimals. But M0 only ranks sponsor classes. The later models use amendment signals such as "days since last update", and a row that exists only because the trial reported again after T is exactly the kind of row those features could learn from. The calibration slope already moved (0.88 to 0.94 at 12 months). A footnote would not have told anyone how large the effect is for a model that does not exist yet.

**Likely interview question.** "How do you know your training labels at an origin contain nothing from the future?"

**Short answer.** By construction and by test. The as-of build filters versions on their post date before any rule runs, so the outcome, the censoring, the lapse logic and the reversal exclusion never see a later version. A test rewrites every version posted on or after T, drops some and adds others, and asserts the training rows of T are identical; a control shows the same rewrite does change the final cohort. I ran the same check on the real warehouse: for the 2016 origin 2.9 million of 4.4 million versions were rewritten and 0 of 399,905 training rows changed, and rewriting from 31 days earlier changed more than 22,000.

**Second question worth preparing.** "Why is one censoring curve not enough for IPCW?" IPCW is unbiased only if censoring is unrelated to the outcome, given what the weights condition on. Here censoring within the horizons comes from records that stop being verified, and that depends on the sponsor class (2.3% of industry trials within five years, 7.9% of trials in the OTHER class, mostly universities and hospitals), which also predicts early stops. With one curve the weights of the most censored class sum to 0.96 of its rows and those of the least censored to 1.03; with a curve per class every class sums to its row count. The effect on M0 is 0.0005 of AUC, which is the honest size of it: the method is right, the correction is small.

**What the review caught.** One of the two reviewers was cut off by a usage limit, so the training labels were checked by me (the real-data rewrite, 16 mutants, of which one needed a new test) and not independently. The other reviewer reproduced the weights with its own implementation to ten decimals and still found gaps: no test had a censoring exactly on the horizon day, so weighting by the curve just before the horizon passed every test; the harness wiring of the weights was only partly tested; and my rule for small classes pools the most censored class with one that is almost never censored at the late landmarks. The tests were added. The pooling rule was left as built, with the options and their measured effect put to Aakrisht, because it is part of how the locked origins will be scored.

## Step 7: Point-in-time features

**What was built.** One command (`uv run python -m trialpulse.features.build`, about 8 minutes, 13 on the first run) that computes 123 features for each of 1,511,335 landmark rows from the version history: design, amendment signals, the sponsor's track record, competition, eligibility statistics, text components and time. A registry lists every feature with its source fields, and `docs/features.md` is generated from it. Each feature at a landmark reads only versions posted on or before that landmark; the two things that are estimated from data (the class rates behind the sponsor's early-stop rate, and the text components) are fitted once per walk-forward origin on that origin's training rows.

**Key decision and why.** Prove point-in-time correctness by attack, not by reading the code. A helper rewrites the registry after a day L: every later version gets another value in every field a feature may read, a later post date and other interventions, a fifth of them are dropped and every trial gets one more version. The features of every landmark on or before L must not change. A test does this for 500 sampled landmarks on a synthetic registry, and a command does it on the real warehouse for each origin (for 2016, 2.9 of 4.4 million versions rewritten and none of the 419,554 earlier rows changed). A feature that reads the current record, a later version or a later outcome cannot survive that, whatever the SQL looks like.

**Rejected alternative and why not.** Computing features per origin, from a copy of the registry cut at the origin. It makes leakage across the origin impossible by construction, but it gives five copies of mostly the same rows and says nothing about leakage inside a training set: a feature at a 2014 landmark that reads a 2015 version is still a leak when the origin is 2016. One table, with a rule per landmark and a test that attacks the rule, covers both.

**Likely interview question.** "Your sponsor track record needs to know which trials belong to a sponsor. How did you handle renames?"

**Short answer.** The registry renames organizations without posting new versions, so the same sponsor shows under two names. I first tried the obvious rule, that names replacing each other on a trial are the same sponsor, and measured it: it merged 6,615 names into one sponsor that contained the largest companies, because most replacements are trials changing hands. The rule I kept reads only what was posted before the landmark: a name passes its record to the name that took at least two of the trials that left it, if those are more than half of the trials that left it or still post under it, and once the first replacement is a year old. Every clause answers a failure I measured or a reviewer found. Without the wait, a large company's record passed to whoever took two of its trials on one day and came back when the company posted again; with 90 days it still happened after a batch hand-over, so the wait is a year, the interval in which the registry asks for an update of every active record. With a plain "the old name has been quiet" test, one late record under the old name erased a real rename. Individuals and placeholder names get no record and fall back to the class rate.

**Second question worth preparing.** "Why TF-IDF instead of embeddings?" The plan allowed embeddings only if they fit in about 2 hours on a CPU. I timed the encoder architecture on the project's machine with random weights (the forward pass costs the same whatever the weights are): 8.7 texts per second at 256 tokens, so about 20 hours for 835,000 distinct texts. The plan's own fallback applies: hashed word counts computed once per text, with the document frequencies and a 32-dimension SVD fitted per origin on training texts only.

**What the review caught.** Two reviewers recomputed the features with SQL of their own and found no mismatch and no feature that reads the future. They found 20 other things, all real. Three are worth remembering. A feature I took from the plan ("start date actual or anticipated") was a calendar proxy: the registry records that field from 2017 on only, just before the test years, so I derive it from the start date instead. My leakage check did not rewrite every field a feature may read, and never moved a post date, so a leak through one of those would have passed; it now covers the whole whitelist and a test requires that. And my calendar-month tests only used landmarks on the first of a month, exactly where month and day arithmetic agree, so five wrong implementations passed them. A test that cannot fail for the bug it names is not a test, and a mutation check (33 one-line faults, 32 caught, one that changes no answer) is how I now confirm that each one can.

## Step 9: Baselines and Cox analysis

**What was built.** The two baselines every later model is measured against, on the development origins only. M0 is the early-stop curve of the trial's sponsor class and nothing else. M1 is a gradient-boosted classifier that sees a trial once, on the day it is registered, with all 123 features. At registration M1 reaches an AUC of 0.68 and 0.70 at 12 months (M0: 0.61 and 0.60) and is calibrated overall (slopes 0.91 and 1.12), though too high for the small sponsor classes. Around them: MLflow tracking for every run (commit, dataset revision, configuration, metrics, result files), two cause-specific Cox models for interpretation with a check of proportional hazards, a results document generated from the result files, and a diagnosis of why the baseline's calibration slope moved when the training labels stopped using hindsight.

**Key decision and why.** M1 trains only on trials registered more than H months before the origin, for a label at H months. The plan says "IPCW classifier", and the textbook reading is: train on every row, give rows with an unknown outcome weight zero, and reweight the rest. That fails here, and I measured how badly: mean predicted risk of 25% against an observed 2%, and the AUC drops from 0.68 to 0.60. Among the trials registered in the last H months, the only ones with a known outcome are those that already ended, so 11% to 14% of them are early stops against 2% to 5% of the older rows. The weights fix the average, and they did (the weighted share of early stops is 2.0% and 2.1%). They cannot fix it for a model that can see when a trial was registered, and every trial the model is later asked about is newer than all of its training rows.

**Rejected alternative and why not.** Weighting by registration period, which is the usual repair when censoring depends on a covariate. Here the censoring is the calendar: given the registration date, a trial registered 3 months before the origin has probability zero of being observed at 12 months unless it ended. The weight would be one over zero. Inverse probability weighting needs every kind of row to have some chance of being observed (positivity), and this design has none for recent controls, so the honest fix is to leave those rows out and say what it costs: the newest training trial is one or two years old. The discrete-time models of the next step lose only 6 months, which is one reason for them.

**Likely interview question.** "You used inverse probability of censoring weights. When are they not enough?"

**Short answer.** When the reason a row is censored is something the model can see. IPCW corrects the average over whatever the weights condition on; mine condition on sponsor class. Administrative censoring is a function of the registration date, and registration year is a feature, so within "recent registrations" the labeled rows are selected on the outcome and no weight can restore the missing ones. I found it because a test on simulated trials compared the mean predicted risk of new trials with their observed rate and the model was 40% too high. Then I ran the literal version on the real data to see the size before writing the rule down.

**Second question worth preparing.** "Your baseline's calibration slope went from 1.25 to 1.46 after you removed hindsight from the training labels. Which number is right?" Both describe something real. I refitted the baseline on hindsight labels with one difference at a time swapped in. One category explains more than the whole move: trials whose record had lapsed on the origin. Built as of the origin, they are censored at their last verified date; hindsight knows that 4 in 10 came back and counts their quiet years. Those records are mostly academic sponsors, so their estimated hazard rises by a third of a percentage point, and since the baseline predicts one number per class and two classes hold 95% of the rows, the slope is the ratio of two small gaps and reacts strongly. The as-of labels are the ones a model could have had on that day, so they stay. Whether a model with features inherits the problem is still open: the registration-only model does not run hot for that class (1.31% against 1.42%), but it has no later landmarks and is hardly exposed to the effect, so it proves nothing. I added a table of predicted against observed risk by sponsor class to every result, and the discrete-time models will be read against it.

**A third, on survival analysis.** "Did you check the proportional hazards assumption?" Yes, and it fails for the covariates that matter: the hazard ratio of industry sponsors for an early stop is 3.1 in the first year after registration and 1.3 afterwards (terminations and withdrawals together; an association, the model says nothing about why). With 118,000 trials the Schoenfeld test rejects for trivial differences too, so next to each test I report the ratio in the two windows, which is the size of the violation and not only its p-value. The Cox models are for reading, not for prediction, and the report says that a single ratio there summarizes a ratio that changes over time. One detail a reviewer found: follow-up is in whole days, so thousands of trials end on the same day, and the usual implementation ranks tied events in row order. My rows are sorted by registration, and registration year is a covariate, so the order leaked into its statistic. Tied days now share one rank.

**What the review caught.** Two reviewers reproduced the numbers with code of their own (one refitted the classifier without calling my fit function and got identical predictions) and found no leak and no wrong headline number. They found 29 other things. Three are worth remembering. First, the tests: of the 112 one-line faults they planted, 51 passed, among them "the classifier's weights come from one censoring curve, not one per sponsor class" and "the censoring groups are decided after the landmark filter", two rules my report said were tested. The tests asserted things that were true but did not depend on the rule; one test's own description named a failure that did not happen. Now a test reads what the library is actually handed. I then had two more reviewers attack the fixes themselves, and 16 of their 25 new faults passed my new tests: the made-up inputs of one test held the same numbers for both horizons, so a table printing the wrong horizon passed. After three rounds and 169 planted faults, one passes, and it changes nothing. Second, a sentence of mine said one sponsor class was overpredicted, while the table beside it showed that nearly all the small classes were, about twofold together. I had summarized a table without reading every row, and the pooled calibration slope hid it because those classes are 5% of the rows. Third, a subtler selection survives my own fix: the registry's lapse rule needs two years to act, so on the prediction date the newest training years have not been thinned yet, while the evaluation rows have. Nothing known on that date removes it, so it is stated and watched and not patched.
